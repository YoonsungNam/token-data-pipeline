지도를 그리며 드러난 것

token-mart-daily 실제 스케줄 — 장부 M15GitHub 기준선은 0 4 * * *. 6c의 10:20은 "토큰 mart가 그 전에 끝난다"는 순서 전제이므로 사내 CronJob 스케줄이 10:20 이전인지 admin 확인이 필요하다 (kubectl get cronjob token-mart-daily -o jsonpath='{.spec.schedule}'). 어느 프리플라이트도 이 순서를 검사하지 않는다.
README 두 곳이 "계정 생성"을 잘못 말한다mart/token-usage/ddl/README.md는 "계정 자체는 collectors accounts.sql에서 기생성"이라 하고, collectors/token-usage/ddl/README.md 1단계는 아직 CREATE USER/CHANGE_ME를 언급한다. 실제로는 어느 파일에도 CREATE USER가 없다 (mart는 동료 소유). 기존 모듈 불변 원칙상 이번 PR에서는 고치지 않았다.
assets/model-catalog/ddl/README.md는 main 그대로신규 dim 4·seed·accounts_metrics.sql·생성기가 이 README에는 없다. 문서는 collectors/token-metrics/ddl/README.md(적용 순서)와 Plan 6a에만 있다.
6a 브랜치는 아직 아무것도 배포하지 않았다PR #14는 DDL·GRANT·seed·생성기·테스트만 추가한다. install.sh ×2, CronJob ×2, Job 템플릿 3, Secret 2, ConfigMap 2는 6b/6c 플랜에 정의돼 있고 코드가 없다. 9/9 게이트 전까지 신규 열은 전부 "예정"이다.
mutation 예산은 정기 실행에서 06b 정기 슬롯은 앵커가 있으면 스킵, 없으면 INSERT만. mutation은 rerun(--replace ≤3/일)과 mart rerun(≤4/일)에서만 발생 — 기존 수집기 예산 45(3×15)·마트 64(4×16) 안에서 계산.
교차검증 P2는 지도 밖의 점선추론엔진 /metrics는 노출 서비스가 소수(장부 M24 ③)라 표본 교차검증 전용(M10). 수집기·마트 어느 테이블에도 적재 경로가 없고, 별도 모듈(설계 #14)이 생기기 전까지는 소비 노드에 점선으로만 닿는다.
사내 호스트·주소·비밀번호·이메일은 싣지 않았다 (Secret·ConfigMap은 이름만). 열 수·ORDER BY·PARTITION은 ddl/company/*.sql의 _local 정의에서, 잡 사양은 k8s/base/cronjob.yaml과 6b/6c 플랜에서 옮겼다.
